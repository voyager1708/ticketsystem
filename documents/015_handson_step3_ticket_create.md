## プログラミングが初めての場合（参考実装あり）

**このリポジトリ（v1-start）には、goal ブランチを参考にしたチケット作成 API の実装がすでに入っています。**

- **エンドポイント**: `POST /api/ext/v1/ticket/create`
- **実装場所**: `app/ticket_service/views.py` の `TicketCreateAPIView`、`app/ticket_service/urls.py` にルート登録済み

**進め方（初めて向け）**

1. **まず動作確認から** — 下記「手順」の **4. Swagger での動作確認** に進み、Swagger から `POST /api/ext/v1/ticket/create` を呼んで 201 / 400 の動きを確認する。
2. **仕様を読む** — `021_ticket_create_api_spec.md` で必須項目（event_name, event_date）とレスポンスの形を確認する。
3. **コードを読む** — `TicketCreateAPIView` の `post` メソッドで、どこで入力チェックをしているか・どこで 201/400 を返しているかをたどる。
4. 余力があれば、手順 2〜3（設計・自分で実装）に挑戦する。

プログラミングに慣れている場合は、以下の「このステップのゴール」から手順 1 に進み、自分で実装してから動作確認してください。

## このステップのゴール

- **エンドポイント**: `POST /tickets/create`（実パスは `POST /api/ext/v1/ticket/create` を想定）
- **入力チェック**を実装し、不正なリクエストでは `400` を返す
- **正常時は `201`**、バリデーションエラー時は **`400`** を返し分ける
- **成功条件**: 生成したチケットの結果（ID やレスポンス body）を、後続の API（例: チェックイン `POST /tickets/{id}/checkin`）で使える形で返す

---

## 手順

### 1. 仕様の確認（5分）

- `documents/021_ticket_create_api_spec.md` の「3. ベースAPIとの整合性」「5. リクエスト/レスポンス」を読む
- 必須パラメータ（例: `event_name`, `event_date`）と任意パラメータを把握する
- 正常レスポンス（201）で返すべき項目（ID や後続 API で必要な情報）を確認する

### 2. 入力チェックの設計（5分）

- 必須項目が欠けている場合 → `400` とエラーメッセージを返す
- 型や形式が不正な場合（例: 日付フォーマット）→ `400` を返す
- 学習用テンプレート（`010_Step1_CreateAccount.md` の「学習用API設計テンプレート」）に沿って、リクエスト項目・正常/異常レスポンスを一度メモする

### 3. 実装（URL・View・Serializer）

- `POST /tickets/create` にルーティングする（または既存の `/api/ext/v1/ticket/create` に合わせる）
- View でリクエスト body を受け取り、Serializer でバリデーションする
- バリデーション成功時: チケット生成処理を呼び、**後続 API で使う情報（例: チケット ID）を含む JSON** を返し、ステータス **201** を返す
- バリデーション失敗時: エラー内容を JSON で返し、ステータス **400** を返す

### 4. Swagger での動作確認

- `/swagger/` を開き、`POST /tickets/create`（または該当パス）を選択
- **正常系**: 必須項目を正しく送信 → **201** とレスポンス body を確認
- **異常系**: 必須項目を省略、または不正な値を送信 → **400** とエラーメッセージを確認

### 5. 成功条件の確認

- 201 で返ったレスポンスに、**後続 API（チェックインなど）で使う識別子（例: チケット ID）** が含まれているか確認する
- その ID を利用して、次の Step 4（`POST /tickets/{id}/checkin`）で検証できる状態になっていれば Step 3 完了
